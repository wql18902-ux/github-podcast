## 可直接复制的任务内容

```text
在 <项目根目录> 执行每日 AI 周节目任务：研究、写稿、检查、MiMo 原速合成、验音频并交付。全程完成，不停在计划或“稿子写好了”。

这是本人于 2026-10-07 认可第二版试听后启用的新任务，替代这条任务原先的“只写稿、不要合成”说明。涉及本节目时，以本任务为准：旧 175 汉字/分钟估时、8500/6500 字闸、十字段/数字行数量、固定每日新闻段和逐文件口播不再适用。旧脚本暂保留供历史链路使用，不修改全局共享 skill。

一、先读取
1. config/audience.md：听众的实际生活约束仍有效；其中“Python、SQLite 等无需解释”的假定已被本人否定。按非专业听众写，不能因为他会用 AI 就假定懂实现术语。
2. output/pilot-ai/ai-week-pilot-v2-script.md 和 ai-week-pilot-v2-breakdown.md：这是本人认可的讲述样本与模型迁移边界。
3. ~/.codex/skills/wang-zhenyu-perspective/SKILL.md、references/behavioral-profile.md，以及本期选用模型所指向的原逐字稿相关段落。模型摘要帮助找原文，不能冒充原文证据。
4. 选题库.md 的困惑、想听的、本周主题、当天排期；output/episodes.log、scripts/blacklist-projects.txt、output/news-covered.md。只追加台账，不改删历史。

二、选题与研究
围绕 AI，每周一个问题，七期从不同角度递进，各期也能独立听。沿用当前周的问题线；把旧排期的工程标题转成值得听众判断的 AI 问题，源码只是证据之一。若当前周主题已用尽，说明理由后选择新的 AI 问题，不被仓库名单绑住。
周六挑一个有可靠来源的当周变化深入讲，其他日子只讲帮助回答本期问题的新闻。周日必须带来新案例检验本周判断，不做六期摘要。
优先真实项目经历、官方记录、公开访谈和源码。核对会变化的事实及来源时间，区分事实、推断、未确认。没有证据的对话、心理活动、结果和本人经历不编造。
选一条主模型，必要时加一条辅助模型。它必须真正改变追问、证据选择和结论；解释为什么适用、能判断什么、何时不适用。不能每期硬套“手段绑架”，不能用模型给听众贴人格标签，也不把模型当科学定律。
检查主案例和主项目是否已讲过；黑名单项目不能当现役主角。以前讲过的项目只可作简短对照，不能重写成新一期。

三、写成可以听的稿子
从一件具体的事情切入，尽早说明为什么值得听。自然地追问、展开、推导、作判断，保留停顿、转折和必要的自我修正。借鉴王振宇的分析与表达方式，保持 AI 讲述者身份，不冒充他本人或编造他的亲历。不靠堆“对吧”和口头禅制造风格。
先讲术语解决的问题，再解释名称；不影响判断的英文、缩写、版本、参数放研究笔记。类比后交代边界。每个案例结束就讲它帮助听众判断什么，不把启发都留到最后，也不强接背词、减脂，不训话。
研究笔记可以技术深入，口播只留帮助理解和判断的细节。不要念写作模板、文件地图、来源网址、Markdown 标题或相关链接。
口播开头包含：“本期声音由人工智能合成，使用王振宇的克隆音色，内容不代表王振宇本人观点。”

四、长度与落盘
成品目标 50–60 分钟，MiMo 原速。认可样本实测约 271 汉字/分钟，备稿可先估 1.36–1.63 万汉字，优先写到约 1.45–1.55 万汉字；这只是预算，最终以音频实测为准。材料不足就补有价值的新案例，不复述凑长、不放慢声音。
用本机日期 YYYY-MM-DD，先写：
- output/<日期>-script.md：阅读稿，末尾有“## 相关”双链。
- output/<日期>-breakdown.md：本期问题、模型原文出处与读取范围、事实取证、案例推导、适用边界、取舍；不要求旧十字段或数字行配额。
- output/<日期>-narration.txt：纯口播正文，去掉标题、信息截止等元数据和“## 相关”及其后内容，保留 AI 合成声明。
另将主题唯一标识、主项目、来源、当前日期、稿件 SHA-256 和检查结果记录到 output/<日期>-episode.json，便于续跑与防重。不要写任何密钥。
核对日期稿与口播输入一致、来源可回查、事实未虚构、模型真正参与推导，再把阅读稿更新到 output/latest-script.md。

五、新任务的状态与防重复
本任务明确授权你维护 output/latest-status.txt；这是新节目对旧“仅 verify-episode.sh 写状态”规则的限定替代。不要运行旧 daily-prepare.sh、episode.py 或 verify-episode.sh，它们会预先记账或套用旧内容闸。
开始前先检查：若上一期处于 MIMO_READY / SYNTHESIZING_MIMO 且尚无完整音频，优先续跑上一期，不覆盖稿子；若已有当前日期、同一稿件 SHA-256 且已验收的成品，复用，不能重新合成。
新节目状态首行只用 MIMO_READY、SYNTHESIZING_MIMO、AUDIO_READY_MIMO、DELIVERED_MIMO 或 FAILED，并写日期与稿件指纹。不要写 OK 前缀——旧豆包与本地兜底只认 OK，让它们自动跳过新节目。
失败必须写 FAILED、失败阶段、原因及可续跑产物路径，不让旧稿保持可合成状态。

六、合成、验收、交付
把本期固定的音频路径写入 episode.json。首次取 python3 scripts/ep_no.py 的期号，文件名 output/audio/<日期>-ep<期号>-mimo-AI合成.m4a；续跑复用已记录路径，不重新取期号。
只运行这一条合成路线：
env -u PYTHONPATH python3 scripts/tts_mimo.py --input output/<日期>-narration.txt --output <已记录的音频路径> --ref voices/mimo-clone-ref.wav
不加 --fresh，不设置 --han-per-min，保留原速；沿用段级缓存续跑。不调用 seed-audio 或 VoxCPM2。
若工具把长命令放后台，继续查看进程和日志直到退出，不能以“已启动”收工。失败时保留段缓存。
合成后用 ffprobe 测真实时长，用 ffmpeg -v error -i <音频路径> -f null - 检查完整解码，并核对输入稿件指纹没有变化。
不到 50 分钟或超过 60 分钟，按实测速率补充新案例或删重复，再合成；不调速凑时长。最多两轮修订；仍不合格就写 FAILED 并保留产物说明情况，不能谎报达标。
过关才写 AUDIO_READY_MIMO，记录实测时长、文件 SHA-256。按项目现有交付方式运行 bash scripts/pipeline.sh upload <音频路径> 上传网易云并备份夸克。注意：当前上传脚本只要一边成功也可能退出 0，不能据此认定两边都成功。必须分别检查网易云和夸克的上传结果，在 episode.json 各自记录成功/失败及可回查的落点；两边都确认成功才写 DELIVERED_MIMO。任一边失败，保留 AUDIO_READY_MIMO 和合格本地音频，明确报告哪一边未传好，下次只重试失败的一边，不重合成，也不重复上传已成功的一边。
音频合格后才向 episodes.log 追加本期 topic:<唯一主题标识> 和新的主项目（已有条目不重复追加）；只有实际讲到的新事件才追加 news-covered.md。补本期期次 page.md 和至少两条双链；先检查是否已存在，重复执行不得多建一期。
最后报告本期问题、用到的模型、稿件与音频路径、实测分钟、上传落点、未解决问题。风格好不好由我听后判断，不能自行宣布“本人已认可整期”。
```
