# 播客深度写稿 · 框架

> 深度 = **供料的具体程度** × **结构的推进强度**。
> 供料决定有多少真东西可讲，结构决定这些真东西能撑多久、听得下去。

## 什么时候用

- 要写一篇「把一个东西讲透」的口播稿或技术长稿
- 稿子写完自己听着觉得空、觉得短、觉得像在复述 README
- 审别人的稿子，要说出「为什么不深」而不是「感觉有点水」
- 定写稿规则、写 prompt、做验收标准

**适用范围**：为「讲解一个系统/一件事物的机制」而写的内容。
**不适用**：闲聊型播客、访谈型播客、纯资讯播报、API 参考文档。
书面长文与口播稿的差异见「可迁移性」一节。

---

## 第一步：诊断是哪一层不够

稿子不深只有三种情形。**先分清再动手，否则会在错的那层使劲。**

| 情形 | 症状 | 缺的是 | 该做什么 |
|---|---|---|---|
| 1 | 讲完架构就没了，每段都很短 | 供料的**事实半边** | 回去读源码/原文，抠具体值 |
| 2 | 说得出文件名和参数，但讲不出「为什么要这样」 | 供料的**why 半边** | 补代价、补反事实、补取舍 |
| 3 | 材料一堆但听着累、记不住、像念说明书 | **成型层** | 重排结构，加驱动性问题与反射 |

**判别动作**：随便挑一个讲过的设计点，连问三句——
1. 「它具体怎么做的？有没有一个具体数字/标识符？」答不上 → 情形 1
2. 「不这么做会有什么问题？代价是什么？」答不上 → 情形 2
3. 前三句都答得上，但讲出来干巴、记不住 → 情形 3

**最常见的误判**：把「稿子短」当成「没写够」，于是要求「写够 8500 字」。
**字数永远是结果，不是手段。** 材料只有 3000 字的量，要求写 8500 字只会得到水稿。

---

## 核心操作：一个设计点 = 四句话

把机制拆到最小可讲的单位，是「设计点」。**每讲一个设计点，按顺序说四件事。**

| # | 说什么 | 怎么做好（技法） | 篇幅 |
|---|---|---|---|
| 1 | **它具体怎么做** | 必须带具体值：常量 / 默认值 / 枚举成员 / 分支条件 / 错误码 / 字段名与类型。**每个核心文件至少贡献一条这样的值。** 讲的时候按「对外是什么 → 内部怎么走 → 为什么这么走」一层层下，一次只下一层 | 200-300 字 |
| 2 | **为什么必须这么做** | 说清「不这么做会怎样」。最好用**异常分支 / 兜底 / 超时 / 重试 / 降级**当切口——正常路径只让你看到函数名，出错的路径才暴露内部假设 | 150-250 字 |
| 3 | **这么做的代价是什么** | 写清「选了什么 / 放弃了什么 / 代价具体落在哪」。**没有代价那半句的不算一条** | 100-200 字 |
| 4 | **换成常见默认做法会怎样** | 一句反事实追问。这一句天然产出「跟默认做法的差异」，是最硬的比较材料 | 150-250 字 |

**一个设计点 ≈ 600-900 字。**
50 分钟量级（约 8500-10500 汉字）≈ 10-12 个设计点 + 开场收尾。

**为什么这条管用**：它把「写得深」翻译成「四件事有没有说全」——
一个能逐条检查的动作，而不是一个感觉。

**最难的是第 2 和第 3 句。** 第 1 句只要读过代码就能写，第 4 句套模板就能写；
只有「为什么必须」和「代价」需要真的想清楚。**这两句也是区分「读过源码」和「看过 README」的分界线**
（Julia Evans 的说法：只列功能不解释 why 是技术解释最普遍的失败模式；而写作者省略 why 的真实原因是
写难、写错显眼、干脆列功能——「一个薄弱的 why，也比没有 why 好得多」）。

**选题的取舍**：只深读「有戏的文件」，不铺目录。
文件职责清单是**骨**，深读是**肉**——铺目录产生的是骨头堆砌。
文件地图可以列 6-8 个核心文件说职责，但**深读只挑 2-3 个**，
标准是「这里面有我看不懂、或者反直觉的地方」。

## 全篇骨架

### 一个驱动性问题
开头抛一个**具体问题**（不是「今天聊聊 X」），中段每一节都在推进它，结尾给一个答案。
写完逐段自检「**这一段推进了那个问题吗**」——没推进就删。

### 从最有戏的点开场，再倒回去（「e」形结构）
画出事件/设计的时间线，挑**最有戏的一点**开场，然后倒回起点补背景，
一路推回开场那个点，越过它继续往前。
（Transom 拆解 99% Invisible 得出的结构，也是「从最反直觉的具体事实切入」的通用做法。）

**动作**：开场讲 2-3 句最反直觉的具体细节，**再**回头交代「这是个什么东西」。
不要把「它是什么」放在第一段。

### 三幕
把一集切三层，制造「在移动」的推进感。两幕太平。

## 节奏与自检

### 事实与反射必须成对
**事实**（发生了什么 / 机制怎么走）与**反射**（所以呢 / 为什么 / 代价）必须交替。
只有事实是流水账，只有反射是空谈。

**动作**：**禁止连续两段只有事实**。每讲完一个机制，下一句必须是反射。

### 定期给具体路标
每 5-8 分钟（口播约每 800-1300 汉字）一句路标，且必须**具体**：
「上段讲入口，这段钻判定逻辑」。「接下来我们继续看」不算路标。

### 定期给反直觉事实
每隔一段来一个听众预料之外的事实，打断预测模式，防催眠。

**红线**：用**直接陈述**的方式落地。**禁用「你以为……其实……」这类翻案句式**——
先立假误解再推翻是最典型的 AI 腔。

### 成稿出声念一遍
念着拗口的地方就是要改的地方；一句话一口气念不完就拆开。

## 机械可查的检查清单

**下表默认按口播稿判。** 写书面长文时，第 5 项（单一驱动性问题）、第 6 项（事实与反射交替）、
第 7 项（路标）与第 8 项（反直觉开场）按「可迁移性」那节放宽或跳过。
审稿或自检时逐条过，前四条能写成脚本。

- [ ] 每个核心文件条目下有 ≥1 个具体值（数字 / 枚举 / 错误码 / 字段名）
- [ ] 每个设计点都写了「代价」那半句
- [ ] 每个设计点都回答了「换成默认做法会怎样」
- [ ] 全文没有出现翻案腔句式（不是…而是… / 你以为…其实… / 表面…实则…）
- [ ] 全篇只有一个驱动性问题，且每段都能对应到它
- [ ] 没有连续两段只有事实（每段事实后必有反射）
- [ ] 每 800-1300 汉字出现一句具体路标
- [ ] 开场前 100 字是最反直觉的具体细节，不是「这是个什么东西」
- [ ] 同一观点只讲一次（换个说法再讲一遍不算推进）
- [ ] 凡二手推断、闭源产品、未亲自验证的内容，都标了来源，或写了「截至写稿时未确认」

## 领域共识 vs 分歧

**共识（所有来源都指向）**：具体优于笼统；解释 why 优于罗列 what；取舍必须给代价；
长内容必须有推进结构；同一观点重复讲不等于深入。

**三处真实分歧**：

1. **广度 vs 纵深**。JustPod 的 Aiolos 说「只要够深入，一个问题也能成好节目」；
   但 NPR 的结构方法论偏多场景、多转折。
   → **按素材量取舍**：能凑 10 个以上设计点就拼盘铺开；只有 2-3 个硬点就纵深钻透。

2. **全篇高密度 vs 留喘息**。声动活泼的徐涛说「每段没增量就像嚼口香糖」；
   但传播实践派主张高密度段落之间要留低密度缓冲。
   → **调和方式**：缓冲段不能是废话，只能是「换个层级说同一件事」（例如从机制层降到直观层），
   而不是复述已说过的内容。

3. **要不要用「失败」开场**。技术写作派推荐用 bug/失败撕开抽象层；
   但口播稿里这样做容易变成翻案腔。
   → **可以讲失败，但直陈事实，不做「揭穿」姿态。**

## 可迁移性：口播稿 vs 书面长文

这套框架为口播稿设计，但大部分成立。**照搬会出问题的是这三条**：

| 机制 | 口播稿 | 书面长文 |
|---|---|---|
| 「e」形结构开场 | 成立（听觉没有回看，必须靠开场抓住） | **不成立**。技术文档、RFC、论文应开门见山，先给结论与范围 |
| 三幕 / 驱动性问题 | 成立 | 弱成立。书面可以按「问题—方案—取舍—边界」分段，不必强造悬念 |
| 出声念一遍 | 必须 | 不适用。改为「朗读关键段落」，检查是否绕口 |

**失败的典型场景**：拿这套框架去写 API 参考文档——读者是来查参数的，
不需要驱动性问题，也不需要反直觉开场，四句话里的第 3、4 句更是完全不需要。
**判断标准**：读者是来「听一个故事/理解一个设计」还是来「查一个事实」。
后者不该用这套。

## 落到 github-podcast（本项目的具体改法）

本项目是「读 GitHub 开源项目源码 → 写口播稿 → 本地 TTS 合成」的单人播客。

**实测校准（2026-09-14 取证）**：

| 形态 | 汉字 | 折合音频 |
|---|---|---|
| 单项目 | 3600-4025 | 21-24 分钟 |
| **三项目拼盘** | **9910** | **≈58 分钟** |

换算口径：**汉字 ÷ 168 ≈ 音频分钟**。**想要 50 分钟量级，拼盘是唯一被验证过的配方。**

**七段骨架按本框架改造**：

| 原骨架 | 怎么改 |
|---|---|
| 1 开场钩子 | 按「e」形结构：从最反直觉的具体事实切入，不写「这项目是什么」 |
| 2 这项目是什么 | 压到 300-500 字，给背景就够 |
| 3 拆解主体 | **主力段**。按项目分段，每个设计点走「四句话」 |
| 4 思维的分野 | 这里集中放最硬的 2-3 条「代价 + 反事实」 |
| 5 AI 范式 | 保持一段讲透。**「范式」是本项目术语，不算黑话** |
| 6 回到你身上 | 落地三问，具体到今天能改的哪一步 |
| 7 一句话带走 | 一条能搬运的判断标准 |

**本项目的红线（写稿时必须守）**：
- 双引号用「」
- 破折号、冒号**保留**（口播停顿信号，TTS 会读成停顿），但克制
- 禁翻案腔：不是…而是… / 并非…而是… / 你以为…其实… / 表面…实则…
- 禁「本质上」「说白了」「这意味着」「换句话说」这类词
- 中文口语，讲给「你」听，不是上课
- 正文不放表格、不留反引号、不直接塞文件路径——文件名先换成听得懂的中文说法

## 反模式（明确禁止）

- **用字数当手段**：材料不够就要求写更长 → 只会得到水稿
- **同一个设计点换五种说法反复讲**：这是「听着水」的第一病根
- **抽象演绎 / 大段比喻 / 人生感悟填字数**
- **把 README 的营销话术当技术内容讲**
- **编造原文里没有的东西**：查不到的写「未确认」，宁可不写不许编
- **只写职责不写 why**（缺第 2 句）
- **只讲选了什么，不讲代价**（缺第 3 句）

## 诚实边界

- 本框架提炼自**写稿方法论**层面的调研，不涉及「文笔 / 语感」这类风格问题。
- **没有实证的分段数学模型**：50 分钟量级的严格节奏模型未找到。
  「每 800-1300 汉字一条路标」「每 3-5 分钟一个钩子」都是经验值，不是实测结论。
- **中文播客侧的来源偏访谈与二手归纳**，比英文侧（Transom / NPR Training 等官方训练材料）弱一档。
  中文侧提供的更多是「什么算好」，而不是「怎么做到」。
- 「技术内容深度」**无学术界的统一量化定义**。本框架用的是实践定义：
  是否触及取舍代价、是否有可验证的证据、是否回答反事实。
- **本框架不覆盖：采访类内容的提问设计、音频后期的声音设计、选题的市场判断。**
- 调研时间：**2026-09-14**，之后的方法论变化未覆盖。
- 有 4 条候选结论因**只有二手来源或无法溯源**被排除，未纳入本框架
  （见 `references/research/05-来源登记.md` 的「未确认清单」）。
  其中一条是「长播客时长由素材量驱动」——本框架采用结构算法（设计点数 × 每点篇幅），
  两者的关系未验证。
